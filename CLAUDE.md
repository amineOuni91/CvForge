# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

CvForge — SaaS CV builder for IT profiles (form editor → real-time A4 preview → pixel-perfect PDF export). Full spec lives in [PLAN.md](PLAN.md); read it for the complete data model, API surface, security rules and phase-by-phase plan. This file tracks build/run commands and architecture as they get implemented — see [progress.md](progress.md) for current phase status.

## Stack

- **Frontend**: Angular (latest), standalone components, signals, zoneless, Vite via `@angular/build`, Tailwind CSS v4 for UI chrome (CV templates use plain CSS with variables, not Tailwind)
- **Backend**: .NET 10, ASP.NET Core Minimal APIs, EF Core 10 + SQL Server (local instance `MSSQLSERVER`)
- **Auth**: ASP.NET Core Identity via `MapIdentityApi<AppUser>()`
- **PDF/HTML export**: Microsoft.Playwright (Chromium headless), renders the same `/print/:id` Angular route used on screen; **DOCX export**: DocumentFormat.OpenXml (native, editable — not a PDF conversion); **TXT/JSON export**: plain C# formatters
- **AI**: NuGet `Anthropic` SDK, `claude-opus-5`, degrades to `503` when `Anthropic:ApiKey` user-secret is unset
- **Import**: UglyToad.PdfPig (PDF) + DocumentFormat.OpenXml (DOCX)
- **Validation**: FluentValidation (backend), Angular Reactive Forms (frontend)
- **Tests**: xUnit + WebApplicationFactory (backend), Vitest via `@angular/build:unit-test` (frontend)

## Architecture

**The CV is one JSON document, not 10 relational tables.** `Cvs` table has just `Id, UserId, Name, Document (nvarchar(max)), CreatedAt, UpdatedAt`. EF Core 10 maps a strongly-typed `CvDocument` C# object graph into the `Document` column via `ComplexProperty(...).ToJson()` / `OwnsMany(...).ToJson()`. This gives one save endpoint instead of ~40 CRUD endpoints, and drag-and-drop reordering is just array order — no `SortOrder` columns to recalculate. Tradeoff (`ponytail:` in PLAN.md §3): no SQL querying into CV content, and every save rewrites the whole document. Only move to relational tables if cross-CV search or collaborative editing becomes a real requirement.

**Authorization is enforced in one helper**, not per-endpoint: `LoadOwnedCv(userId, cvId)` filters `WHERE Id = @cvId AND UserId = @currentUserId` in the query itself (never filtered after loading). A CV owned by someone else returns `404`, never `403` (which would confirm existence). See `AuthorizationTests` in the backend test suite — this is the one thing that must never regress.

**PDF/HTML fidelity comes from reusing the screen renderer; DOCX does not.** `GET /api/cvs/{id}/export/pdf` (and `/export/html`) load the CV, launch Playwright against a reused headless Chromium instance, navigate to `{FrontendOrigin}/print/{id}` with the document injected via `AddInitScriptAsync("window.__cv = ...")` (no auth token needed — backend injects data directly), wait for `window.__cvReady === true` (fonts loaded), then call `page.PdfAsync` with `PreferCSSPageSize: true` (or extract+inline the rendered HTML/CSS for `/export/html`). The `/print/:id` Angular route renders the CV alone (no chrome) using `@page { size: A4; margin: 12mm }`. `/export/docx` deliberately does **not** go through Playwright — it's built natively from `CvDocument` via `Services/DocxExport/` so the result is a real editable Word document, not a PDF screenshot; see the export notes below. `ponytail:` the on-screen preview shows a continuous 210mm column with a page-break marker every 297mm rather than real JS pagination — it flags overflow but doesn't reflow like Chromium will; only build real pagination if this gap becomes a real problem.

**AI never invents facts.** Three enforced layers (system prompt forbids adding unlisted facts; each endpoint receives only the text to transform, never an "invent an experience" prompt; UI always shows suggestions beside the original with explicit Accept/Ignore — nothing is auto-written). ATS scoring is deterministic C# rules (not LLM) for reproducibility; the LLM only turns the rule outputs into natural-language recommendations, so that feature still works in degraded mode (no API key).

**All 5 CV templates share one CSS variable contract**: `--cv-primary`, `--cv-secondary`, `--cv-font`, `--cv-scale`, `--cv-gap`, set on the root container from `CvSettings`. Switching templates never touches data; customization logic is written once for all five.

**UI language vs. CV language are independent.** The app UI (buttons, menus) follows a bilingual FR/EN toggle app-wide. The CV's own section headings ("EXPÉRIENCE" vs "EXPERIENCE") follow `CvSettings.CvLanguage`, stored per-CV.

## Notes d'implémentation

- **`.slnx` pas `.sln`**: .NET 10 `dotnet new sln` génère le nouveau format XML `.slnx`. Toute commande référençant `CvForge.sln` doit utiliser `CvForge.slnx`.
- **`UseHttpsRedirection()` désactivé en `Development`** dans `Program.cs` : le certificat de dev n'est pas approuvé par défaut, et le frontend appelle l'API en `http://localhost:5145` — une redirection vers `https://` casserait le fetch. Activé normalement en production.
- **CORS** restreint à `http://localhost:4200` via une policy nommée `Frontend`.
- `AppDbContext : IdentityDbContext<AppUser>` (Phase 1) ; le mapping `ToJson()` de `CvDocument` sur la table `Cvs` a été ajouté en Phase 3 — voir plus bas pour le détail.
- **Avant tout `dotnet build` manuel**, arrêter le process `CvForge.Api.exe` en arrière-plan (`Get-Process CvForge.Api | Stop-Process -Force`) : le build échoue sinon avec un verrou de fichier Windows sur l'exe. `dotnet watch` n'a pas ce problème (il recompile lui-même à chaud).
- **Auth = Bearer token**, pas de cookies (`login?useCookies=false`) : SPA sur un port différent de l'API. Tokens persistés en `localStorage` (`cvforge.accessToken` / `cvforge.refreshToken`), attachés par `core/auth.interceptor.ts`, refresh automatique sur `401` (une seule tentative de retry).
- **`DisplayName` n'est pas géré par `MapIdentityApi`** (DTO register = email/password seulement). Un endpoint maison `GET/PATCH /api/auth/me` (`Endpoints/AuthEndpoints.cs`) le lit/modifie séparément ; c'est la page Profil qui le renseigne après inscription.
- **`forgotPassword` ne déclenche l'envoi (le log) que si l'email du compte est confirmé** — comportement Identity standard anti-énumération, pas un bug. En dev, confirmer via le lien loggé à l'inscription avant de tester le flux de reset.
- **i18n minimal démarré dès la Phase 2** (`core/i18n.service.ts`, signal de langue + dictionnaires plats `locales/fr.ts`/`en.ts`, pipe `t`) plutôt qu'en Phase 14, pour éviter de retoucher tous les écrans après coup. Toute nouvelle page doit utiliser le pipe `t` avec une clé dans les deux fichiers de locale, pas de texte UI en dur.
- La page racine Angular (`app.ts`) est maintenant juste `<router-outlet />` ; le vrai routing et les 6 premières pages (login/register/forgot/reset/dashboard/profile) sont en place depuis la Phase 2. Templates inline (pas de fichiers `.html` séparés) pour ces petits composants de formulaire.
- **`CvDocument` est mappé en JSON**, pas en tables relationnelles : `AppDbContext.OnModelCreating` fait `OwnsOne(c => c.Document, d => { d.ToJson(); d.OwnsOne(...); d.OwnsMany(...); })`. Toute nouvelle propriété ajoutée à `CvDocument` (ou ses types possédés) n'a besoin d'**aucune migration** tant qu'elle est un type scalaire ou une collection simple — seul un nouveau type owned imbriqué nécessite d'appeler `.OwnsOne`/`.OwnsMany` explicitement dans le mapping.
- **`dotnet ef migrations add` place le dossier en `CvForge.Api/Migrations/`** (racine du projet), pas `Data/Migrations/` comme suggéré dans PLAN.md §8 — comportement par défaut de l'outil, laissé tel quel.
- **`sqlcmd -i script.sql` sur Windows peut corrompre les caractères accentués** (é/è/à/ç… deviennent des séquences type "Ã©") si le fichier `.sql` est écrit en UTF-8 simple (sans BOM) : `sqlcmd` devine alors la page de code au lieu de détecter l'UTF-8, même avec un littéral `N'...'`. Deux parades qui marchent : `sqlcmd -f 65001 -i script.sql` (force la page de code UTF-8), ou plus fiable, écrire le `.sql` en UTF-16LE avec BOM (`sqlcmd` le détecte automatiquement). Repéré en écrivant manuellement du contenu de CV (texte français) en base via script — **toujours vérifier après coup** avec `SELECT CASE WHEN Document LIKE '%Ã%' THEN 'CORRUPTED' ELSE 'CLEAN' END ...` plutôt que de faire confiance à l'absence d'erreur de `sqlcmd`.
- **Dupliquer un CV** (`POST /api/cvs/{id}/duplicate`) fait un round-trip JSON (`Serialize`/`Deserialize`) sur `Document` : un objet owned EF Core ne peut pas être partagé/suivi par deux entités `Cv` en même temps, il faut une copie indépendante.
- Toute nouvelle route touchant un CV doit passer par `db.LoadOwnedCvAsync(userId, cvId)` (`Data/CvAuthorization.cs`) — jamais charger par `Id` seul puis vérifier après coup. Un CV non possédé doit renvoyer `404`, jamais `403`.
- **Ne jamais déclencher un appel HTTP de façon synchrone dans le constructeur d'un service Angular qui est lui-même injecté par un `HttpInterceptorFn`** (via `inject(AuthService)` dans l'intercepteur). Ça crée une résolution DI ré-entrante (le service est encore en cours de construction) qui lève une erreur silencieusement avalée — dans `core/auth.service.ts`, `fetchMe()` au démarrage est donc appelé via `queueMicrotask()`, pas directement dans le constructeur. Ce bug provoquait une déconnexion silencieuse à chaque F5 alors que le token restait valide côté serveur ; corrigé en Phase 4/5, voir [progress.md](progress.md) pour le détail du diagnostic.
- **`CvStore` (`editor/cv-store.ts`)** est la seule source de vérité du document en cours d'édition (signal), avec autosave debounced 1,5 s (`PUT /api/cvs/{id}`). Toute section de formulaire mute via `store.update(doc => ({...doc, champ: ...}))`, jamais de mutation directe.
- **`ui/` (composants réutilisables) construits au fil des besoins réels, pas par anticipation** : `tag-input.ts` (Phase 4, réemployé 5 fois — technologies, missions, réalisations, compétences par catégorie, centres d'intérêt), `modal.ts` (Phase 9, confirmation de suppression), `skeleton.ts` (Phase 14, états de chargement), `toast.ts` (Phase 14, notifications globales). Pas de Button/Card/Select génériques — rien n'en a eu besoin.
- **`tag-input.ts` supporte le drag & drop entre tags** (`cdkDropList cdkDropListOrientation="horizontal"` sur les puces) en plus de l'ajout/suppression — comme le composant est partagé, ça réordonne les tags dans toutes les sections qui l'utilisent en une seule modification. Vérifié par interaction pointeur réelle dans le Browser pane.
- **`tag-input.ts` supporte aussi l'édition d'un tag existant** : double-clic sur une puce → elle devient un `<input>` pré-rempli (`editingIndex` signal), `Entrée`/perte de focus valide (texte vide = suppression du tag, comme pour l'ajout), `Échap` annule. Double-clic plutôt que simple clic pour ne pas entrer en conflit avec le drag (`cdkDrag`) ni avec le bouton `×`. Comme pour le drag & drop, ça s'applique à toutes les sections qui réutilisent le composant en une seule modification.
- `template-host.component.ts` fait le `@switch` sur `templateKey` entre les 5 templates (`modern` par défaut, `minimal`, `executive`, `tech`, `ats`) — voir plus bas pour le détail par template.
- **Repères de page dans la preview** : une seule ligne pleine (pas un pointillé littéral) tous les 297mm via `repeating-linear-gradient` CSS, pas de mesure JS de la hauteur réelle du contenu — cohérent avec la simplification déjà documentée dans PLAN.md §6 (`ponytail:` pagination non réelle, juste un repère visuel).
- **`.cv-section` ne doit JAMAIS avoir `break-inside: avoid`** dans `cv-base.css` — repéré en session post-Phase 14 : avec un CV à contenu réel (plusieurs expériences détaillées), la section "Expériences" dépasse largement une page A4 ; `break-inside: avoid` force alors Chromium à pousser toute la section sur la page suivante plutôt que de la couper, laissant un grand espace vide en bas de la page précédente (ex. "Profil" seul sur la page 1, "Expérience" entière page 2+). `break-inside: avoid` reste correct sur `.cv-entry` (une seule expérience, taille raisonnable) et `break-after: avoid` sur `.cv-section-title`/`.cv-entry-title` (évite un titre orphelin) — seule la granularité section était trop large.
- Dates de CV : `<input type="month">` natif (pas de composant date-picker custom) pour le format `YYYY-MM` ; affichage formaté via `templates/format-month.ts` selon `CvSettings.CvLanguage` (« Mars 2021 » / « March 2021 »), indépendant de la langue de l'UI (`I18nService`).

- **Les 5 templates sont tous branchés** dans `templates/template-host.component.ts` (`@switch` sur `templateKey` : `modern` (défaut), `minimal`, `executive`, `tech`, `ats`). Chacun filtre `visibleSections()` depuis `settings.sectionOrder`/`hiddenSections` indépendamment — pas de logique partagée au-delà de `cv-base.css`/`font-stacks.ts`/`format-month.ts`, volontairement (5 layouts réellement différents, dont un deux-colonnes pour `executive`).
- **Le template `ats` ignore délibérément `Settings.PrimaryColor`/`SecondaryColor`** (texte forcé en noir) — c'est voulu, pas un oubli, pour rester parsable par un ATS.
- **Aucune police custom n'est réellement chargée** (pas de `@font-face`/Google Fonts) : le sélecteur de police change la variable CSS `--cv-font` mais retombe sur les fallbacks système de `templates/font-stacks.ts`. `ponytail:` à corriger seulement si le rendu visuel exact devient un vrai besoin.
- **Drag & drop** (`@angular/cdk/drag-drop`) : sections (`section-list.component.ts`), expériences et catégories de compétences (`sections/experiences.section.ts`, `sections/skills.section.ts`) sont réordonnables via poignée `⠿` + `moveItemInArray` ; les tags à l'intérieur d'un `tag-input.ts` sont réordonnables directement (voir plus haut). Vérifié par interaction pointeur réelle dans le Browser pane (session post-Phase 14) pour le réordonnement des tags — le drag des sections/expériences/catégories reste vérifié seulement structurellement.
- **Les 5 templates ne rendaient ni `missions`/`achievements` ni `gitHub`** (et l'ATS n'affichait même pas `linkedIn`) avant une passe de correction post-Phase 14 : l'éditeur sauvegardait bien ces champs (`experiences.section.ts`, `personal-info.section.ts`) mais aucun `@if`/`@for` correspondant n'existait dans certains templates, donc la donnée disparaissait silencieusement de la preview/PDF. Corrigé dans les 5 fichiers `templates/*/*.component.ts` ; missions et réalisations sont affichées en deux listes `<ul class="cv-list">` séparées et labellisées (bilingue FR/EN via `lang()`), pas fusionnées dans une seule liste. Nouvelles classes `.cv-list`/`.cv-list-label` dans `cv-base.css`, partagées par les 5 templates. **Symptôme à surveiller** : si un champ ajouté à `CvDocument` n'apparaît pas dans la preview alors qu'il se sauvegarde bien, vérifier d'abord que les 5 templates le rendent, pas seulement un ou deux.
- Masquage de section : bouton `👁`/`🚫` dans `section-list.component.ts`, bascule `CvSettings.HiddenSections` — chaque template respecte ce filtre indépendamment.

- **PDF = Playwright pilotant `/print/:id`**, pas une lib de génération PDF séparée : `Services/PdfService.cs` lance Chromium headless une seule fois (singleton `IAsyncDisposable`, réutilisé entre requêtes — confirmé par mesure : 1er appel ~3.2s, appels suivants <1s) et navigue vers la même route Angular que la preview, avec les données injectées via `window.__cv` (pas de jeton d'auth à fabriquer côté Playwright). **`playwright install chromium` doit avoir été exécuté** dans l'environnement (`backend/CvForge.Api/bin/Debug/net10.0/playwright.ps1 install chromium --with-deps`) sinon `PdfService` échoue au premier appel.
- **La route `/print/:id` n'est PAS protégée par `authGuard`** (volontairement) — elle lit `window.__cv` injecté par le backend en priorité, et ne retombe sur un `GET /api/cvs/{id}` authentifié que si un utilisateur humain connecté l'ouvre directement par erreur.
- **`CvStore.downloadExport(format)` force un `saveNow()` avant de télécharger** (généralisation de l'ancien `downloadPdf()`) : le fichier est généré côté serveur depuis ce qui est en base, pas depuis l'état en mémoire du navigateur — sans ce flush, un export juste après une frappe pourrait rater l'autosave (debounce 1,5s).
- **Export multi-format** (`GET /api/cvs/{id}/export/{format}`, `format` = `pdf|docx|txt|html|json`) — remplace l'ancien endpoint dédié `/pdf` (supprimé, plus rien ne l'appelait à part `PdfEndpoints.cs` lui-même ; le dashboard et l'éditeur ciblent maintenant `/export/pdf`). Endpoints/Services concernés :
  - `Endpoints/ExportEndpoints.cs` — un seul endpoint paramétré, 400 si le format n'est pas dans la liste blanche, 404 (jamais 403) via `LoadOwnedCvAsync` comme partout ailleurs.
  - **`Services/DocxExport/`** : DOCX **natif** via `DocumentFormat.OpenXml` (pas une conversion PDF→DOCX via LibreOffice — écarté explicitement pour rester un vrai document Word éditable). `SingleColumnDocxBuilder` (paramétré police/couleur/majuscules) couvre modern/minimal/tech/ats ; `ExecutiveDocxBuilder` a sa propre implémentation (seul template 2 colonnes, un vrai tableau Word avec cellule de gauche ombrée). `DocxHelpers.cs` porte les briques communes.
  - **`ponytail:` piège OOXML rencontré et corrigé** : `RunProperties`/`TableBorders` etc. imposent un **ordre strict des éléments enfants** (`w:rPr` : rFonts, b, i, color, sz, dans cet ordre précis ; `w:tblBorders` : top, left, bottom, right, insideH, insideV). Faire `runProps.AppendChild(new Bold())` **après** avoir construit `RunProperties` avec `FontSize` casse la validation Word (`OpenXmlValidator` lève `Sch_UnexpectedElementContentExpectingComplex`) même si Word peut parfois l'ouvrir quand même en l'ignorant silencieusement. Toujours construire la liste d'enfants dans l'ordre du schéma **avant** de construire l'élément composite, jamais `AppendChild` après coup pour un enfant optionnel qui doit s'insérer au milieu.
  - `CvTextHelpers.cs` (labels de section FR/EN, formatage de date) est partagé entre le DOCX et `Services/TxtExportService.cs` (rendu texte brut, indépendant des 5 templates).
  - **HTML export** : même rendu Playwright que le PDF (`PdfService.RenderCvHtmlAsync`), mais le CSS appliqué est extrait via `document.styleSheets` côté page et inliné dans un `<style>` pour produire un fichier autonome, ouvrable sans le serveur Angular.
  - **`Tests/ExportTests.cs`** : vérifie les 5 formats (200 + bon `Content-Type`), le 400 sur format inconnu, le 404 cross-utilisateur, et surtout — pour chaque template — que le DOCX généré passe `OpenXmlValidator` sans erreur (c'est ce test qui a détecté le piège d'ordre des éléments ci-dessus).

- **Les miniatures du dashboard sont des blobs authentifiés**, pas des `<img src="...">` classiques : `GET /api/cvs/{id}/thumbnail` exige un Bearer token (même contrôle de propriété que tout le reste), donc `dashboard.ts` les récupère via `HttpClient` + `URL.createObjectURL`, et les révoque dans `ngOnDestroy`. Pas de cache — régénérées à chaque chargement du dashboard via Playwright (`PdfService.RenderThumbnailAsync`, ~1s/miniature). `ponytail:` à mettre en cache (par `UpdatedAt`) si ça devient un problème de latence perçue.
- **`ui/modal.ts`** est le 2e composant UI réutilisable (après `tag-input.ts`) — créé en Phase 9 pour la confirmation de suppression, pas avant, conformément à la règle YAGNI déjà notée plus haut.

- **SDK `Anthropic` (NuGet officiel) — forme d'API non documentée localement, découverte par réflexion .NET** plutôt que devinée (voir `progress.md` Phase 10 pour la méthode). Points clés retrouvés : `new AnthropicClient(new ClientOptions { ApiKey = key })`, `client.Messages.Create(new MessageCreateParams { Model = Model.ClaudeOpus5, MaxTokens, System, Messages = [new MessageParam { Role = Role.User, Content = text }] })`, réponse `message.Content` = liste de `ContentBlock` dont `.Value` peut être un `TextBlock` (`.Text`). Si une future phase doit étendre `AiService`, préférer une reconnaissance par réflexion similaire à une supposition sur la forme de l'API plutôt que de deviner en cas de doute.
- **`AiService.IsAvailable` gate tout appel IA** — jamais d'exception qui remonterait en 500 : les 3 endpoints IA renvoient **503** explicite si `!IsAvailable`. `GET /api/ai/status` permet au frontend de griser les boutons *sans* consommer un appel réel (`editor/ai.service.ts`, signal `available`).
- **Aucun appel IA réel n'a pu être testé dans cet environnement** (pas de clé configurée, mode dégradé conforme au contexte initial du projet). Le chemin nominal (succès du modèle) reste à valider dès qu'une clé est disponible — voir `progress.md` Phase 10.
- **Rate limiting natif ASP.NET Core** (`AddRateLimiter`, 10 req/min par utilisateur) sur tout le groupe `/api/ai` — le même mécanisme (`RequireRateLimiting`) sera réutilisé pour `/api/import` en Phase 11, conformément à PLAN.md §5.

- **Import PDF/DOCX (`POST /api/import`) ne persiste rien** — il renvoie un `CvDocument` structuré que le frontend passe ensuite à `POST /api/cvs` pour créer un vrai CV. **Pas d'écran de vérification séparé** : le frontend navigue directement vers l'éditeur après création, qui sert lui-même d'écran de relecture champ par champ (déjà entièrement éditable avec preview live depuis les Phases 4/5) — écart assumé avec le wireframe de PLAN.md §9, pour éviter de dupliquer l'éditeur dans un second composant.
- **Tout parsing de fichier utilisateur (PDF/DOCX) doit être enveloppé dans un try/catch** renvoyant 400, jamais laissé remonter en 500 — un fichier avec les bons magic bytes peut quand même être corrompu en interne (`UglyToad.PdfPig.PdfDocument.Open` peut lever `PdfDocumentFormatException`). Voir `Endpoints/ImportEndpoints.cs`.
- **Pour tester l'extraction d'un format de fichier structuré (docx, xlsx, etc.), générer le fichier de test avec la même bibliothèque qui l'écrit ailleurs** (ici `DocumentFormat.OpenXml`), jamais en zippant des fichiers XML à la main (`Compress-Archive` ne produit pas un paquet OPC valide reconnu par `System.IO.Packaging`).
- **`FileValidator.cs` (magic bytes, limites de taille) existe mais l'upload de photo n'est pas implémenté** — `POST/DELETE /api/cvs/{id}/photo` est listé dans le tableau API de PLAN.md §5 mais n'apparaît dans aucune des 14 phases de PLAN.md §11. Écart connu entre le tableau d'API et le plan de phases, signalé à l'utilisateur ; `MaxPhotoSizeBytes` est déjà prêt (2 Mo) si cette fonctionnalité est demandée plus tard.

- **`POST /api/ai/analyze` ne renvoie jamais 503** — contrairement à `improve-text`/`bullet-points`/`summary`. Les 5 scores sont **toujours** calculés par `Services/AtsAnalyzer.cs` (100% C# déterministe, aucun appel IA). Seul le texte des recommandations dépend de l'IA, avec repli sur les messages bruts des règles échouées si `!ai.IsAvailable` — le panneau ATS reste donc utile même sans clé API.
- **`AtsAnalyzer` mesure la parseabilité structurelle (`atsScore`), pas la richesse du contenu (`contentScore`, séparé)** — un CV vide sans photo/sans section masquée peut avoir un `atsScore` élevé tout en ayant un `contentScore` de 0. C'est voulu : ce sont deux axes différents.

- **`backend/CvForge.Tests` fait tourner l'app réelle contre une base SQL Server dédiée `CvForgeTests`** (pas de mocks, pas d'in-memory provider) — séparée de la base de dev `CvForge`, migrée automatiquement au premier accès via une fixture de collection xUnit (`Infrastructure/DatabaseFixture.cs`, migration une seule fois pour toute la suite). `Program.cs` expose `public partial class Program {}` en bas de fichier pour que `WebApplicationFactory<Program>` fonctionne malgré les top-level statements.
- **Commandes de test** : `dotnet test backend/CvForge.Tests` (43 tests : `AuthorizationTests`, `CvCrudTests`, `AtsAnalyzerTests`, `FileValidatorTests`, `ExportTests`) et `npm test --prefix frontend -- --watch=false` (18 tests).
